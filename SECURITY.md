# Security model

## Ключевая граница доверия

Аналитический агент может только создать `ProposalBundle`. Этот объект не является
заявкой брокеру. Торговый токен доступен только отдельному запуску исполнителя,
который принимает полный digest сохранённого пакета, а не параметры заявки.

Подтверждение создаётся отдельным явным сообщением пользователя в Codex и связано
с SHA-256 отпечатком точного пакета заявок. Допустима только фраза
`ПОДТВЕРЖДАЮ ПАКЕТ <полный digest>`; «давай», «ок» и согласие с рекомендацией не
подходят. Любое изменение заявки делает старое подтверждение недействительным.
Квитанция записывается атомарно и только один раз. Сама команда подтверждения не
отправляет заявку; после неё Codex отдельно запускает исполнитель с тем же digest.

До первой заявки исполнитель заново проверяет портфель, доступность выпуска,
торговую сессию, свежесть котировки и стакана, достаточность денег или бумаг и
весь машинный мандат. Изменение данных блокирует весь пакет. UUID заявки
детерминирован от digest и номера позиции; повторный запуск сначала читает её
статус в БКС. Секреты в локальный журнал не попадают.

## Секреты

- Refresh- и access-токены БКС нельзя передавать в чат.
- Токены нельзя хранить в Git, `.env`, SQLite или журналах.
- Для локального MVP read-only refresh-токен хранится plaintext в
  `.local/secrets/` с правами `600`; каталог и файл исключены из Git.
- Локальный `.env` содержит только путь к файлу, а не значение токена.
- Путь к файлу можно передавать в argv; значение токена — нельзя.
- Для чтения портфеля и для торговли используются разные refresh-токены.
- Аналитический процесс получает только read-only токен.
- Ротированный refresh-токен атомарно сохраняется в тот же приватный файл до
  следующего сетевого запроса.

## Операции, которых нет в модели

- вывод денежных средств;
- перевод активов;
- изменение реквизитов и доступов;
- маржинальные операции;
- фьючерсы и опционы;
- рыночные заявки;
- покупка иностранных активов.

## Остаточный риск исполнения

Корзина заявок БКС не атомарна. При ошибке в середине пакета исполнитель
запрашивает отмену ранее созданных активных заявок, но частичное или полное
исполнение до отмены необратимо. Клиентский `order_valid_until` также требует,
чтобы исполнитель продолжал работать; после прерывания Codex должен запустить
безопасную сверку, которая не умеет создавать новые заявки.

Контрактные тесты покрывают одноразовое подтверждение, отсутствие торговой
авторизации без него, блокировку при изменении стакана, ротацию токена до заявки,
защиту от дублей, частичный сбой пакета, аварийную отмену и отмену по дедлайну.
